# Plan notes

**Rule and where it lives.** `mcp-server/app/services/platform_api.py::comparable_results`, used by `throughput_compare` and tested in `mcp-server/tests/test_platform_api.py::test_comparable_results_keep_only_the_identical_config`. A peer must match on model, gpu_type, **gpu_count**, precision, input_tokens, output_tokens, workload_type and concurrency. It must also have `status='success'`, a **non-null `total_token_throughput`**, and a different run_id. Parallelism, server and node do not count. The server-side filter is `app/routers/results.py::_build_filter_conditions`, and it skips any falsy value, so a 0-token target matches every token setting.

**How I counted.** Configuration = the 8-field key above. For each configuration I counted the distinct runs that count as usable peers: failed rows and success rows with null throughput are excluded, so gpu_count 1 and gpu_count 2 runs are never pooled. I set the number of new runs to reach at least 3. The simulations are in `/tmp/work/cfg.py` and `/tmp/work/sim.py`. After the plan, every one of the 112 configurations has at least 3 usable runs.

**Sweeps.** h100/llama31 gc1 fp8 2048/512 +1. mi210/llama31 gc4 +2. mi210/llama33 gc8 +2. rtx5090/qwen gc1 fp8 +2. rtx5090/qwen gc4 bf16 +1, only at c32/64/128, the levels where failed runs leave just 2 usable runs. rtx5090/qwen gc4 fp16 +1, because one run has null throughput and one failed. t4/tinyllama 512/512 +1, for the same reasons. That is 10 sweeps under the code's rule.

**Why 14.** Under the code's rule, the two 0/0 configurations (t4 tinyllama, mi210 llama31 gc8) already have peers through the token wildcard, or get them from the sweeps above. If a 0 token count is read literally, each needs 2 more runs. I added 2 sweeps for each (+4, total 14) so the floor holds under both readings, and that fits the 14-sweep budget exactly. Note: with 14 sweeps you cannot also give every *existing* run 3 peers excluding its own run; that would take 17. So the floor is met in the per-configuration sense.
